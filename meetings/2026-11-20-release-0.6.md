### 3.1 #45 Item revisions

**Need.** An engineer must know which state of an item was released and that it does not change silently while the rest of the product moves on. Raised in the backlog cleanup; general to any product.

**Exists.** Each item has its own version independent of commits (TE-01.1); its history is `git log -- <folder>`; released states are the protected branch (`architecture.md:33`); a revision label (A, B, C) is a type field (CO-02.8); maturity is `status` (CR-12, `requirements.md:42`). Missing: nothing stops a `released` item's content from changing while it stays `released`.

**Proposal.** New **TE-05.3:** "`impact` shall also list as `released` each item whose `status` at base is in `plm.yaml`'s `released_states` (default `[released]`) and whose version changed while its status did not; exit 1 if any." Touches `src/impact.ts:12`, `src/cli.ts:129`. Assemblies selecting a revision belong to #40/#43 (0.8).

**Options.** **A** no code: README paragraph mapping revision, history, label and release to the above; 0 counted words, ¼ window; immutability remains review discipline. **B (recommended)** A plus TE-05.3: about +40 `documents/`, +60 `src/`+`test/`, ½ window; CI catches the silent change. **C** explicit revision records that assemblies reference: a new storage concept and data format, 2+ windows, duplicates Git history. **Architecture:** none for A/B (`impact` gains an exit 1 on findings, CL-05.2); C is one.

### 3.2 #46 Baselines

**Need.** A released product configuration must be reproducible and comparable later.

**Exists.** A Git tag is an immutable snapshot of every item, link, confirmation and test run; every command runs on a checkout of it; `plm impact <tag>..HEAD` compares it with today (TE-05.1); approvals are the host's reviews (`architecture.md:37`); CI can run `validate`, `suspects` and `report coverage` on the tag (README:34).

**Options.** **A (recommended)** no-go, closed with the README paragraph of #45: 0 counted words. **B** a global `--at <commit>` for read commands via `snapshotAt`: about +25/+40, ¼ window; duplicates `git worktree add`. **C** a baseline record of item versions and approvals: about +120/+200, 1½ windows, duplicates the tag, approvals are process (`decisions.md:6`), architecture change. External artifacts in other repositories are out of scope for all.

### 3.3 #59 Change requests

**Need** (issue): record a change's impact and that every resulting suspect link was reviewed.

**Exists.** `plm impact <range>` (TE-05.1); each confirmation records `by`, `on`, `commit` and `reason` (TE-02.1); `plm suspects` exits 1 while any link is suspect (`src/cli.ts:125`), so CI on the pull request (README:34) is the evidence; the change itself is a host issue and merge request.

**Options.** **A (recommended)** no-go: a change request is process, not product data (#64); CR-13 drops "support issues and change requests and" (about −6 words). **B** `impact` exits 1 while links in the range stay suspect: duplicates `suspects`. **C** a change item type: process in the product tree, about +100/+150, 1 window.

**Options.** **A (recommended)** close with these answers; the rules go into #40/#43's *done when*; no database for now. **B** keep it open as a checklist in 0.8. **C** a database or transaction layer: architecture change without a failing case.

### 3.5 #2 HTML view and generated documents

**Proposal.** New **CL-01.8:** "`report document [<item>]` shall print the VS-03.1 document as Markdown, IDs linking to their files." The function moves to `src/`; VS-03.1 cites CL-01.8. A host renders Markdown in a browser or phone; a converter prints it.

**Options.** **A** `plm export html <dir>`, a static site of all pages as in the issue: about +150/+300, 2 windows, a second rendering beside the extension's. **B (recommended)** CL-01.8: about +25 `documents/`, +200 `src/`+`test/` and −140 `extension/`, 1 window less what is moved; one document, two front ends. **C** defer to 0.9 with the UI redesign (#67). **Architecture:** none for B; A adds an output style.
