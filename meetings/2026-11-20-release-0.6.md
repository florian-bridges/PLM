### 3.1 #45 Item revisions

**Context.** Can an engineer trust that a released item stays as released? Nothing notices today when a `released` item's files change while it stays `released`; 0.7 is about releases.

**Exists.** Each item has its own version independent of commits (TE-01.1); its history is `git log -- <folder>`; released states are the protected branch (`architecture.md:33`); a revision label (A, B, C) is a type field (CO-02.8); maturity is `status` (CR-12, `requirements.md:42`).

**Proposal.** New **TE-05.3:** "`impact` shall also list as `released` each item whose `status` at base is in `plm.yaml`'s `released_states` (default `[released]`) and whose own files changed while its status did not; exit 1 if any." Own files, the `changed` list (`src/impact.ts:20`): a changed version alone would flag every released assembly when any part changes. TE-05 then cites CR-12 and US-11 besides CR-13. README:40 "reports only" changes to say that `impact` fails on such items. Touches `src/impact.ts`, `src/cli.ts:129`.

**Options.** **A** no code: README paragraph mapping revision, history, label and release to the above; 0 counted words, ¼ window; immutability remains review discipline. **B (recommended)** A plus TE-05.3: about +45 `documents/`, +60 `src/`+`test/`, ½ window; CI catches the silent change. **C** explicit revision records that assemblies reference: a new storage concept, 2+ windows, duplicates Git history; assemblies selecting revisions are #43 (0.8).

### 5.1 #40 Occurrences and quantities

**Context.** An assembly uses the same part several times, each use with its own reference designator, position or other properties; changing a use must not change the part. Today an item is either nested (one folder, one place) or in `uses` by ID only: no quantity, no per-use data. Listing an ID twice in `uses` passes `validate` (tried on a generated repository).

**Options.** **A** no code: quantity by repeating the ID, per-use data in a type's list field (CO-02.8, CO-03.3): 0 words; nothing checks that the field's entries name used items, and a part's identity and its uses stay mixed. **B (recommended)** a `uses` entry may be `{item, quantity, ref, …}` besides an ID, extra keys from the type; `validate` keeps reporting unknown items (`src/validate.ts:63`) and adds duplicate `ref`s; the occurrence's data is in the assembly's `item.yaml`, so changing it changes the assembly's version, not the part's; `show --down` gives quantities, and a total per part over a subtree. About +60 `documents/`, +250 `src/`+`test/`, 1–1½ windows. **C** occurrences as items with an `instance-of` link: each use gets an ID, links and ports, but one folder per fastener; about +100/+400, 2 windows.

**Architecture: yes** (B and C change the format that the schema, `usesOf` and the version read as plain IDs; B keeps them valid). #43's selection rules and port connections of one occurrence (#29) build on it. **Go in principle; details in a feature review prepared during 0.7.**

### 5.3 #43 Variants and effectivity

**Context.** One product exists in variants and serial-number or date ranges that use different components or revisions, and the exact definition of a given unit must be resolvable from defined inputs. Today a commit gives one deterministic definition (TE-01.1); a variant can be its own root sharing items through `uses`; a delivered unit can be a tag. Missing: choosing between alternatives inside one tree, and effectivity.

**Options.** **A** no code: README pattern (variant = root assembly, changed form/fit/function = new item, delivered unit = tag): 0 words; serial ranges stay outside PLM. **B (recommended)** #40's `uses` entries gain an applicability condition on configuration parameters declared in `plm.yaml` (e.g. `variant`, `serial`), and `show --down` and `report` take `--config <param>=<value>`; `validate` reports a selection that is ambiguous or empty; the #66 rules go into the *done when*. About +80 `documents/`, +300 `src/`+`test/`, 1½–2 windows. **C** B plus `uses` pinned to an item's version at a commit, resolving earlier revisions side by side: a second storage of history beside Git, 3+ windows.

**Architecture: yes** (new data format; brings back a configuration concept removed in `ea3257d`, so the review states what differs). **Go in principle; details in the feature review with #40.**
